# Contexto del Proyecto y Revisión de Código (`holidays-tracker-ws`)

Este documento resume la arquitectura, el modelo de dominio, los flujos de autenticación y los hallazgos de la revisión de código actual para mantener el contexto entre sesiones de desarrollo.

---

## 1. Contexto General y Arquitectura

- **Propósito**: API REST para gestionar usuarios, autenticación sin contraseña para empleados (invitaciones de un solo uso y códigos de recuperación por email), panel administrativo con token Bearer y gestión de vacaciones.
- **Stack**:
  - Node.js `>= 20` (ESM `"type": "module"`)
  - Fastify `^5.0.0` (`@fastify/cors`, `@fastify/cookie`, `@fastify/swagger`, `@fastify/swagger-ui`)
  - PostgreSQL (`pg.Pool`)
  - Correo SMTP (`nodemailer`)
  - Despliegue con Docker (`node:20-alpine`) y Jenkins (`Jenkinsfile`) para entornos `dev` (puerto `3001`) y `prod` (`main`, puerto `3000`).

### Estructura del Código
- `src/server.js`: Configuración de Fastify, CORS (`*.maisonzaro.com` HTTPS, `localhost:4200` y `FRONTEND_ORIGIN`), Swagger en `/docs`, hook global `preHandler` para autenticar la cookie `ht_session`, registro de rutas bajo `/api` y manejador global de errores.
- `src/db.js`: Carga de variables de entorno (`ENV_FILE` o `.env`) y conexión `Pool` a PostgreSQL.
- `src/lib/security.js`:
  - Generación de tokens (`32 bytes` en `base64url`) y hash `SHA-256`.
  - Firma y validación de tokens Bearer de administrador mediante `HMAC-SHA256` (`ADMIN_TOKEN_SECRET`), con validez de **8 horas**.
  - Gestión de cookie HTTP-only `ht_session` (TTL de **8 horas**, `sameSite: 'lax'`).
  - Middlewares (`requireAdmin`, `requireSession`, `requireAdminOrSession`).
- `src/routes/`:
  - `admin.js`:
    - `POST /api/admin/login`: Valida `ADMIN_PASSWORD` y devuelve token Bearer.
    - `GET /api/usuarios`: Lista todos los usuarios excluyendo cargos de administrador (`Administrador`, `Administradora`, `admin`).
    - `GET /api/usuarios/pendientes`: Lista todos los datos de los usuarios con invitación enviada pendiente de activar (`sesiones.estado = 'proceso'`).
    - `POST /api/usuarios`: Crea un usuario en `usuarios`.
    - `POST /api/sesiones/invitaciones`: Envía invitación por email a todos los usuarios sin sesión `autorizado`.
    - `POST /api/usuarios/:usuarioId/invitacion`: Envía invitación individual a un usuario.
  - `auth.js`:
    - `POST /api/sesiones/activar`: Canjea el `codigo` de invitación por la cookie `ht_session` y envía un código de recuperación por email.
    - `POST /api/sesiones/recuperar`: Canjea `email` + `codigoRecuperacion` por una nueva cookie `ht_session` y rota el código de recuperación por email.
    - `POST /api/sesiones/solicitar`: Marca la sesión como `solicitado` y notifica por correo a `ADMIN_EMAIL` (puede llamarlo el propio usuario o el administrador indicando `usuarioId`).
    - `POST /api/sesiones/cerrar`: Revoca la sesión y el código de recuperación de un `usuarioId` (solo administrador); requiere solicitar o enviar una nueva invitación para volver a acceder.
  - `vacations.js`:
    - `GET /api/vacaciones`: Devuelve las vacaciones del usuario autenticado, o de todos/filtradas por `?usuarios=...` si es administrador.
    - `POST /api/vacaciones`: Inserta entre 1 y 366 fechas (`YYYY-MM-DD`) de forma idempotente (`ON CONFLICT DO NOTHING`).
- `src/services/`:
  - `userService.js`: Consultas e inserciones en `usuarios`.
  - `sessionService.js`: Máquina de estados en `sesiones` (`proceso` -> `autorizado` -> `solicitado`) con bloqueo de fila (`FOR UPDATE`) y expiración deslizante de 8 horas (`updated_at`).
  - `vacationService.js`: Validación de fechas e interacción con la tabla `vacaciones`.
  - `emailService.js`: Transporte SMTP perezoso (`getTransporter()`) y plantillas de texto para invitación, recuperación y aviso al administrador.

### Tablas de Base de Datos
```sql
CREATE TABLE usuarios (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    nombre VARCHAR(100) NOT NULL,
    apellidos VARCHAR(150) NOT NULL,
    cargo VARCHAR(120) NOT NULL,
    email VARCHAR(254) NOT NULL,
    tipo_vacaciones VARCHAR(50) NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE sesiones (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    usuario_id BIGINT NOT NULL,
    token_hash CHAR(64) NOT NULL,
    request_token_hash CHAR(64) NOT NULL,
    recovery_token_hash CHAR(64),
    estado VARCHAR(20) NOT NULL DEFAULT 'solicitado',
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT sesiones_estado_valido CHECK (estado IN ('solicitado', 'proceso', 'autorizado'))
);

CREATE TABLE vacaciones (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    usuario_id BIGINT NOT NULL,
    anio SMALLINT NOT NULL,
    fecha DATE NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

### Flujo de Sesiones
1. **Invitación / Petición de sesión (`issueInvitation`)**:
   - Invalida cualquier sesión previa asignando un hash aleatorio a `token_hash` y `recovery_token_hash = NULL`.
   - Genera el token de petición y almacena su hash SHA-256 en `request_token_hash`.
   - Establece `estado = 'proceso'` y envía el enlace por correo electrónico.
2. **Activación (`activateSession` en `POST /api/sesiones/activar`)**:
   - Identifica al usuario por `s.request_token_hash = hashToken(codigo)` con `s.estado = 'proceso'`.
   - Genera el token de sesión (`token_hash`), el código de recuperación (`recovery_token_hash`) e invalida el `request_token_hash`.
   - Pasa el estado a `'autorizado'`.
   - Devuelve en la respuesta JSON los datos del usuario, el `token` de sesión y el `codigoRecuperacion` (además de fijar la cookie HTTP-only `ht_session`).
3. **Recuperación (`recoverSession` en `POST /api/sesiones/recuperar`)**:
   - Valida el `recovery_token_hash` y `estado = 'autorizado'`.
   - Rota el token de sesión y el código de recuperación, devolviendo el nuevo código en la respuesta.
4. **Cierre / Revocación (`revokeSession` / `requestNewSession`)**:
   - Elimina la sesión activa e invalida recovery token (`recovery_token_hash = NULL`), dejando `estado = 'solicitado'`. Requiere una nueva invitación para volver a acceder.

## 2. Hallazgos de la Revisión de Código

### Correcciones Aplicadas
1. **Validaciones de esquema devuelven HTTP 400 (`src/server.js`)**:
   - `app.setErrorHandler` ahora detecta errores de validación (`error.validation` o `error.statusCode === 400`) y responde con `400 Datos de entrada no válidos.` en lugar de `500`.
2. **Transaccionalidad en envío de correo de recuperación (`src/services/sessionService.js`)**:
   - En `activateSession` y `recoverSession`, `sendRecoveryEmail` se ejecuta antes de `COMMIT` para que un fallo SMTP haga `ROLLBACK` y no invalide el código previo del usuario.
3. **Revocación completa de sesión (`src/services/sessionService.js`, `src/routes/auth.js`, `docs/api.md`)**:
   - Al ejecutar `POST /api/sesiones/cerrar` (`revokeSession`), el usuario pierde tanto la sesión activa como el código de recuperación (`recovery_token_hash = NULL`, `estado = 'solicitado'`), debiendo solicitar o recibir una nueva invitación. Además, `requestNewSession` y `revokeSession` usan `INSERT ... ON CONFLICT (usuario_id) DO UPDATE`.
4. **Manejo de `usuarioId` inexistente en `POST /api/vacaciones` (`src/routes/vacations.js`)**:
   - Captura el error PostgreSQL `23503` (`foreign_key_violation`) y responde con `404 Usuario no encontrado.`.

### Puntos Pendientes / Recomendaciones Futuras
1. **Script `dev` en `package.json` incompatible con Windows**:
   - El cambio local `"dev": "ENV_FILE=.env && node --watch src/server.js"` falla en `cmd.exe`/PowerShell en Windows y es redundante porque `src/db.js` ya usa `.env` por defecto.
2. **Seguridad y Limpieza**:
   - **Falta de Rate Limiting**: Endpoints sensibles (`/api/admin/login`, `/api/sesiones/activar`, `/api/sesiones/recuperar`) no tienen protección contra fuerza bruta en la aplicación (`@fastify/rate-limit`).
   - **Consulta de sesión en cada request (`src/server.js:81-84`)**: El hook `preHandler` global ejecuta `authenticateSession` incluso en rutas públicas o administrativas si el cliente envía la cookie `ht_session`.
   - **Documentación en `README.md`**: Documenta una respuesta antigua de `GET /api/vacaciones` (con `nombre`, `apellidos`, `cargo` y sin autenticación).
